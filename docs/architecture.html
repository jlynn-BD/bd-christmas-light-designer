Christmas Light Designer: what it is built with

One Node.js app on Render serves the customer app, the sales tool and the dashboards. It calls one AI service for the pictures and four others for data, email and the CRM.

The stack, top to bottom

Who uses itany phone, tablet or computer

Customers

Public design flow at the root address. Embedded on the WordPress site in an iframe.

Sales team

Design Studio at /team and daily numbers at /team/daily. Shared team password.

Owner and staff

Analytics dashboard at /admin. Separate shared password.

HTTPS, through Cloudflare (Render's front door)
Front endruns in the visitor's browser

HTML, CSS, JavaScript

Plain files, no framework and no build step. Express serves them as they are.

Browser features

Canvas shrinks photos and draws the decorations. postMessage talks to the WordPress page.

Address lookup

Nominatim (OpenStreetMap) suggests addresses, called straight from the browser. Free, no key.

JSON and photo uploads to the app's own API
Back endRender web service, one always-on instance

Node.js + Express

One app, ES modules. Routes for the customer flow, /team and /admin.

Safeguards

Per-visitor and daily limits on AI use, a spam trap on forms, and an email alert if Google stops answering.

Files and images

Photos resized with sharp, PDFs built with pdfkit, uploads read with multer.

Worth raising in the meeting

  • One instance. Usage limits are kept in memory and mirrored to Postgres, so running several instances would need shared state such as Redis.
  • Model lifetime. Google retires older Gemini models over time; the image model name is one line to change when that happens.
  • Accounts. The team and admin areas use shared passwords, not individual logins.
  • Address lookup. Nominatim is a free service with fair-use limits; a paid address API would replace it at higher volume.
